AI Agent 如何与外部工具交互，目前有两个方向：MCP（Model Context Protocol）和 CLI。前者是 Anthropic 2024 年底推出的标准化协议，一度被称为 AI 界的 Type-C 接口；后者是几十岁的命令行界面，最近被重新发现。

## MCP 的问题

MCP 的核心机制是客户端-服务器架构。MCP Server 启动时向 Client 发送所有工具的定义（名称、描述、参数 Schema），Client 把这些定义塞进模型的上下文中。

这个设计有四个实际问题：

**上下文臃肿**。连接 3 个 MCP Server，仅工具定义就占用约 143K token。在 200K 的模型上，72% 的上下文被工具定义吃掉。Agent 还没开始干活就已经满了。更严重的是，随着工具数量增加，工具选择的准确率从 43% 下降到 14% 以下。

**架构复杂**。MCP 涉及多个独立进程和网络边界，初始化不稳定，认证流程繁琐。使用多个工具就需要在每个工具上重新认证，Agent 无法统一管理。

**安全风险**。CoSAI 发布的《MCP 安全白皮书》指出，MCP 存在三类架构级漏洞：间接提示注入、工具投毒、Rug Pull 攻击。安全研究人员已发现近 7000 个暴露在公网的 MCP 服务器，约半数没有任何授权控制。

**被动工具设计**。MCP 工具是预先配置好的，Agent 无法主动发现新工具或探索更高效的用法。

## CLI 的优势

CLI 的做法是「按需加载」。Agent 先执行 `gh --help` 看有什么命令，需要时再 `gh pr --help` 看子命令，最后才执行具体操作。信息按需加载，不是开局全塞。

实测表明，CLI 方案比 MCP 方案便宜 17 倍，可靠性接近 100%。

CLI 的其他优势：

- **组合能力强**：多个命令通过管道组合，不需要额外代码
- **LLM 天生熟悉**：训练数据包含大量 Unix 文档和 shell 脚本，模型天生认识 git、curl、grep
- **可调试**：工程师可以直接在终端跑同样的指令，确认 AI 看到了什么
- **生态成熟**：数十年工程实践，标准化错误码和输出格式

## 三种工具形态的区别

| 维度 | Skill | MCP | CLI |
|------|-------|-----|-----|
| 核心作用 | 告诉 AI 懂什么 | 告诉 AI 怎么接 | 告诉 AI 怎么做 |
| 实现方式 | Markdown 指令文件 | JSON-RPC + Server | 标准化命令接口 |
| Token 消耗 | 极低 | 极高 | 按需加载 |
| 稳定性 | 高 | 中 | 极高 |
| 调试难度 | 低 | 高 | 极低 |

## 大厂的选择

飞书开源了官方 CLI，200 多条指令，涵盖 11 个业务领域。Google 推出了 Google Workspace 的 gws CLI。Zilliz 发布了向量数据库 CLI。

这些选择揭示了一个趋势：CLI + Skills 模式正在成为企业级 Agent 工具的默认模式。原因很现实：AI 要真正进入业务流程，就必须具备执行能力，而 CLI 命令清晰、无歧义、易自动化。

## 混合架构

MCP 并非已死，CLI 也不是要取代它。一个值得关注的趋势是混合架构：用 CLI 处理高频、简单的执行任务，用 MCP 处理需要标准化集成的复杂场景。mcpkit、unmcp 等桥接工具可以把 MCP Server 降级为 CLI 命令，让这种混合架构成为可能。
